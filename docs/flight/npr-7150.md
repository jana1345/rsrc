# NPR 7150.2 & software assurance

::: tip Why this matters
NASA NPR 7150.2 is the software engineering procedural requirement that shows up in lunar-lander job descriptions. You do not need to memorize it. You need to understand software criticality classes, the lifecycle evidence it expects, and how to map your project’s practices to that language without overclaiming.
:::

## Learning objectives

- Explain the purpose and scope of NPR 7150.2.
- Distinguish software classes A–E and what drives them.
- Map lifecycle activities to evidence artifacts.
- Explain software assurance and IV&V.
- Build a tailoring/compliance crosswalk for a small project.
- Avoid the common overclaim.

## What NPR 7150.2 is

NPR 7150.2 is NASA’s procedural requirement for software engineering. It establishes requirements for:

- software lifecycle processes,
- requirements and design,
- implementation and integration,
- verification and validation,
- configuration management,
- quality assurance,
- safety and security,
- acquisition and supplier management,
- training and risk management.

It applies to NASA software and is often flowed down to contractors. A commercial lunar lander is not automatically bound by it, but the structure is a useful benchmark and a common interview vocabulary.

## Software classes

NPR 7150.2 classifies software by criticality, from **Class A** (highest) to **Class E** (lowest). The class drives the rigor of the lifecycle, documentation, reviews, testing, and assurance.

The classification is based on the consequences of failure, including:

- human safety,
- mission loss,
- major facility or system damage,
- significant cost or schedule impact,
- performance/quality impact only.

Exact class definitions and tailoring rules are in the NPR and the companion software engineering handbook. Do not guess a class for a real program; use the program’s classification process.

For a lunar lander, the descent guidance and flight control software is typically high-criticality. A ground analysis script or a developer tool is much lower. The same team can produce both, but they should not receive the same process weight.

## Lifecycle evidence

| Phase | Typical evidence |
| --- | --- |
| **Concept** | Concept of operations, software architecture, risk list |
| **Requirements** | Software requirements specification, traceability, interface requirements |
| **Design** | Architecture/design description, interface control documents, analysis |
| **Implementation** | Source code, coding standard, static analysis, unit tests |
| **Integration** | Build records, integration test plan/results, configuration index |
| **Verification** | Test plans, procedures, logs, coverage, requirements trace |
| **Validation** | Mission-level scenarios, independent review, acceptance |
| **Operations** | User guide, operations procedures, anomaly reports |
| **Maintenance** | Change requests, regression results, release notes |

The evidence should be **objective**: a test log, a coverage report, a review record, a signed configuration index. A slide that says “tested” is not evidence.

## Software assurance and IV&V

**Software assurance** is the set of planned and systematic activities that give confidence that the software is safe, secure, and reliable. It is broader than testing:

- independent review and audit,
- process compliance,
- hazard analysis,
- static analysis,
- configuration management,
- problem reporting and disposition,
- supplier oversight.

**IV&V** is independent verification and validation: a team outside the development team performs analysis and testing. It is most valuable when the software is high-criticality and the development team is too close to the design.

For a small project, you can approximate the spirit:

- have someone else review the requirements and tests,
- run static analysis and coverage,
- keep a problem-report log,
- archive the build and test evidence,
- write a hazard analysis for the descent modes.

## Tailoring

NPR 7150.2 allows tailoring. A small project does not need every document, but it should document:

- which requirements apply,
- which are tailored out and why,
- what evidence replaces them,
- who approved the tailoring.

A tailoring matrix is a table:

```text
Requirement | Applicable? | Tailoring | Evidence | Approval
NPR 7150.2 §... | Yes | None | SRS, trace matrix | ...
NPR 7150.2 §... | No | Small-team process | Peer review record | ...
```

This is the honest way to use the standard. “We follow NPR 7150.2” without a matrix is a slogan.

## A crosswalk for your capstone

| Activity | Your evidence |
| --- | --- |
| Requirements | `docs/requirements.md` with IDs and test links |
| Architecture | `docs/architecture.md` with data flow and rate groups |
| Coding standard | `.clang-tidy`, compiler warnings, MISRA subset |
| Unit tests | `tests/` with coverage report |
| Integration tests | SIL harness with logs |
| Verification | Trace matrix and test report |
| Configuration management | Git tag, build script, artifact hash |
| Problem reporting | `docs/problems.md` with dispositions |
| Safety | Hazard analysis and fault tree |
| Independent review | A peer review record or a second-agent review |

You do not need to call it “NPR compliant.” You can say: “I used NPR 7150.2 as a checklist to structure the evidence.”

## Interview language

Good:

- “I classified the descent software as high-criticality and applied requirements traceability, unit/integration testing, coverage, and fault injection.”
- “I tailored the documentation for a small project and recorded the rationale.”
- “I can show the trace matrix, test logs, and build record.”

Bad:

- “I know NPR 7150.2” (without examples).
- “We were compliant” (without a tailoring matrix and audit evidence).
- “Testing proves it is safe” (testing supports confidence; it does not prove safety by itself).

## Practice

1. Read the NPR 7150.2 table of contents and pick five requirements relevant to your capstone.
2. Build a tailoring/crosswalk table with evidence for each.
3. Write a hazard analysis for three descent faults: stale nav, stuck throttle, and altimeter dropout.
4. Map each hazard to a detection, isolation, and recovery action.
5. Ask someone to review the evidence package and list what they cannot verify.
